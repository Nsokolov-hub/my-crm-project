# Реактив CRM

CRM для небольшой компании, продающей и закупающей химическую продукцию. В одном интерфейсе работают клиенты и поставщики, заявки и позиции, квоты, расчёты, коммерческие предложения и счета, оплаты, согласования, поставки, задачи и обсуждения.

**Текущий статус:** сборка готова к ручной приёмке владельцем компании. Автоматические проверки и пробный запуск на чистой базе описаны в [отчёте](docs/acceptance-report.md). Формулы, ставки, валюты и права нужно настроить перед рабочими расчётами.

Начните с [руководства пользователя](docs/user-handbook.md): оно объясняет продукт, рабочий процесс и проверку каждой из семи ролей.

Что учесть при обновлении установленной системы, описано в [журнале изменений](CHANGELOG.md).

[Изменения от 15 октября 2026](docs/business-update-2026-10-15.md): счёт как КП, каталог отчётов, фильтры задач, плановый объём, «Не делить расходы» и сбор колонок.

[Изменения от 1 октября 2026](docs/business-update-2026-10-01.md): отдельная база обзвона, контакты, импорт исходных таблиц и квот, внутренние коды, документы с логотипом и запуск заказа независимо от оплаты.

Для подробной ручной проверки используйте [функциональный тест-план](docs/manual-functional-test-plan.md): в нём приведены тестовые данные, порядок действий, ожидаемые результаты и критерии приёмки.

Для передачи проекта другой команде используйте [инструкцию запуска из архива и проверки семи ролей](docs/handover-deployment.md). Она описывает создание чистого стенда и отдельных случайных паролей без включения секретов в архив.

Для установки выберите отдельное руководство: [локально в Docker](docs/install-local-docker.md) или [на VPS с доменом и HTTPS](docs/install-hosting-vps.md). Оба описывают первый запуск, проверку сохранения данных, обновление и резервную копию.

## Быстрый запуск на новом компьютере

Понадобятся Docker и Docker Compose. Команды выполняйте в корне клонированного репозитория:

```bash
python3 scripts/init-env.py
docker compose build api web
docker compose up -d --no-build
docker compose ps -a
```

Подождите, пока `db`, `clamav`, `api` и `web` станут `healthy`, а `migrate` завершится с кодом `0`. Первый запуск ClamAV может занять несколько минут. `worker` должен оставаться в состоянии `Up`.

Создайте первого пользователя. Команда запросит пароль в терминале; используйте собственный пароль не короче 12 символов. Флаг `--all-roles` даёт владельцу доступ ко всем разделам для первоначальной настройки и проверки:

```bash
docker compose exec api python -m app.bootstrap \
  --email owner@example.com --name 'Владелец' --all-roles
```

Откройте [CRM на этом компьютере](http://127.0.0.1:8080/) и войдите под созданным пользователем. Адрес API для разработчика: <http://127.0.0.1:8000/api/docs>.

В **Настройках → Организация** добавьте организацию продавца и заполните реквизиты в обычных полях. В **Ролях и правах** выберите доступные сотруднику действия, а в **Правилах работы** настройте причины отказа; результаты обзвона ограничены пятью вариантами. В **Клиентах** создайте клиента и поставщика, затем первую заявку и её позиции. В **Финансовых профилях** укажите действующие для вашей компании ставки и условия в форме, сохраните черновик, проверьте расчёт на контрольном примере и только затем опубликуйте профиль. Дальнейший путь и ожидаемые результаты приведены в [сценарии ручной приёмки](docs/manual-acceptance-small-team.md).

Для остановки приложения используйте `docker compose stop`; при следующем запуске — `docker compose up -d`. Данные хранятся в Docker volumes. Перед реальной эксплуатацией проверьте создание резервной копии по [инструкции](docs/deployment.md).

Если меняете стандартный веб-порт `8080`, добавьте фактический адрес страницы в `ALLOWED_ORIGINS` файла `.env` и пересоздайте контейнер API: `docker compose up -d --no-build --force-recreate api`. Иначе браузер откроет интерфейс, но сохранение форм будет отклонено проверкой источника запроса.

## Проверка исходного кода

Для разработки нужны Python 3.13 и Node.js 24. Зависимости backend для разработки ставятся из `backend/requirements-dev.lock` (`pip install -r backend/requirements-dev.lock` в виртуальном окружении), после чего:

```bash
DATABASE_URL=sqlite:// PYTHONPATH=backend pytest backend/tests -m 'not postgres and not integration' -q
ruff check backend scripts
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend test
pnpm --dir frontend build
```

Контракт API описан в `docs/openapi.json`, его пересобирает `python3 scripts/export_openapi.py`. Типы TypeScript для фронтенда генерируются из него командой `pnpm --dir frontend run api:types` в `frontend/src/lib/api-schema.d.ts`. CI проверяет, что код, документ и типы совпадают. Модели ответов (`response_model`) пока описаны для сессии и пользователей; остальные эндпоинты типизируются по мере перевода на них.

Зависимости backend перечислены в `backend/pyproject.toml`: рабочие — в `[project].dependencies`, инструменты тестов и проверок — в группе `dev`. Точные версии закреплены в `backend/requirements.lock` (его ставит Docker-образ) и `backend/requirements-dev.lock` (те же версии плюс инструменты). После изменения `pyproject.toml` выполните `python3 scripts/lock_backend.py` в окружении разработки; CI проверяет актуальность файлов флагом `--check`.

Тесты с маркером `postgres` требуют отдельной тестовой PostgreSQL-базы. Весь обычный набор тоже можно прогнать на PostgreSQL: задайте `TEST_DATABASE_URL=postgresql+psycopg://…` — каждый тест получит собственную схему, как в CI. Тесты с маркером `integration` требуют выделенной среды для проверки восстановления, переноса истории или worker; они не входят в короткий цикл проверки повседневной CRM.

Файлы `.env`, базы данных, пароли и пользовательские вложения не входят в Git. Не применяйте демонстрационный профиль к реальным счетам, пока ваши правила расчёта не проверены на контрольных примерах.
