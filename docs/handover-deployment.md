# Передача проекта и демонстрационный запуск

Эта инструкция рассчитана на команду, получившую архив с исходным кодом CRM. Для первого запуска Git не требуется. Архив содержит приложение и инструкции, но **не содержит** рабочую базу компании, вложения, `.env` и готовые пароли.

После распаковки сначала прочитайте `README.md`. Для подробного порядка установки выберите [локальный Docker](install-local-docker.md) или [сервер с доменом и HTTPS](install-hosting-vps.md). Пользовательское руководство находится в `docs/user-handbook.md`, а его версия для чтения и печати — в `docs/user-handbook.pdf` внутри передаваемого ZIP.

## Что потребуется

- Docker с командой `docker compose` и доступ к интернету для первой загрузки образов и зависимостей.
- Python 3 на компьютере, где распакован архив. Внешние Python-библиотеки для двух подготовительных скриптов не нужны.
- Свободные порты `127.0.0.1:8080` (интерфейс), `8000` (API), `54329` (PostgreSQL) и `3310` (ClamAV). При необходимости их можно изменить через `CRM_HTTP_PORT`, `CRM_API_PORT`, `CRM_DB_PORT`, `CRM_CLAMAV_PORT` в `.env`.
- Рекомендуется не менее 4 ГБ ОЗУ и 10 ГБ свободного места. Первая инициализация ClamAV может занять несколько минут.

Все команды далее выполняются **из корня распакованного проекта**. Не используйте работающую базу компании для демонстрационного наполнения.

## Запуск чистого стенда для прохода по ролям

1. Распакуйте архив в новую папку и перейдите в неё. Сгенерируйте отдельные случайные секреты для этой установки:

   ```bash
   python3 scripts/init-env.py
   ```

   Скрипт создаёт приватный `.env` и не перезаписывает его при повторном запуске. Не отправляйте этот файл вместе с архивом.

2. Соберите и запустите приложение:

   ```bash
   docker compose build api web
   docker compose up -d --no-build
   docker compose ps -a
   ```

   Дождитесь, пока `db`, `clamav`, `api` и `web` станут `healthy`, `worker` будет `Up`, а `migrate` завершится с кодом `0`. Проверьте интерфейс по <http://127.0.0.1:8080/> и готовность API по <http://127.0.0.1:8000/ready>.

3. **Только на новой пустой базе** создайте демонстрационные учётные записи:

   ```bash
   python3 scripts/setup_demo_roles.py
   ```

   Будут созданы семь сотрудников: Администратор, Руководитель, Владелец расчётов, Менеджер продаж, Закупщик, Логист и Финансовый контролёр. У каждого ровно одна роль и новый случайный пароль. Адреса и пароли появятся на компьютере запуска в `.runtime/demo-role-credentials.txt` с правами доступа `0600`; в терминал они не печатаются. Файл исключён из Git и **не должен** входить в передаваемый архив.

   Если в базе уже есть пользователи или роли, скрипт откажется работать и ничего не изменит. Повторный запуск также не меняет пользователей или пароли и не перезаписывает файл доступов. Для нового демонстрационного стенда используйте отдельную чистую установку; не удаляйте тома существующей установки ради повторного запуска.

   Если изменили веб-порт, передайте фактический адрес в файл доступов: `python3 scripts/setup_demo_roles.py --url http://127.0.0.1:НОВЫЙ_ПОРТ/`.

4. Откройте <http://127.0.0.1:8080/> и последовательно войдите под каждым пользователем из файла. После проверки одной роли выйдите из CRM перед входом под следующей. Права действительно различаются: отсутствие раздела или отказ в запрещённом действии — ожидаемый результат. Если браузер хранит сеанс, используйте выход из аккаунта либо отдельное приватное окно.

## Маршрут проверки каждой роли

Демо-база не содержит заказов, контрагентов и финансовых ставок. Это позволяет команде увидеть, что создаётся вручную, а что входит в приложение. Для сквозного сценария сначала настройте организацию продавца и рабочие справочники под Администратором, создайте клиента и заявку под Руководителем или Менеджером продаж, затем переключайтесь между ролями. Используйте [подробный функциональный тест-план](manual-functional-test-plan.md), [короткий чек-лист приёмки](manual-acceptance-small-team.md) и [руководство по проекту](user-handbook.md).

| Роль | Что проверить |
| --- | --- |
| Администратор | Настройки, сотрудники, роли и права, справочники. Коммерческие разделы могут быть недоступны этой роли — это нормальное разделение обязанностей. |
| Руководитель | Заявки всех сотрудников, задачи, согласования, аналитика и назначение ответственных. |
| Владелец расчётов | Финансовые профили, расчёты и шаблоны документов. Перед публикацией профиля самостоятельно задайте и проверьте ставки, формулы и правила округления. |
| Менеджер продаж | Собственные и предоставленные в доступ заявки, клиенты, звонки, задачи, коммерческие документы и заявление оплаты. |
| Закупщик | Каталог, поставщики, запросы цен и закупочные предложения. |
| Логист | Волны/поставки и связанные задачи. |
| Финансовый контролёр | Подтверждение оплаты и аналитика. |

## Если стенд нужен для реальной работы

На рабочей базе **не запускайте** `setup_demo_roles.py`. Вместо него создайте владельца с собственным паролем:

```bash
docker compose exec api python -m app.bootstrap --email owner@company.example --name 'Владелец' --all-roles
```

Команда запросит пароль от 12 символов; потом владелец создаст сотрудников через интерфейс. До выпуска реальных КП и счетов заполните организацию продавца, подтвердите правила финансового расчёта и проверьте контрольный пример. Для резервного копирования и обновления используйте [техническую инструкцию](deployment.md).

## Данные и остановка

`.env` и `.runtime/demo-role-credentials.txt` находятся на компьютере команды. База и файлы CRM живут в Docker volumes этой установки. `docker compose stop` останавливает приложение без удаления данных; `docker compose up -d` запускает его снова. Команда `docker compose down -v` удаляет тома с данными, поэтому для обычной остановки её не используйте.

При изменении `CRM_HTTP_PORT` укажите новый адрес в `ALLOWED_ORIGINS` файла `.env` и пересоздайте API-контейнер. На другом компьютере `127.0.0.1` означает его собственный адрес: для внешнего доступа нужен отдельно настроенный HTTPS-прокси и соответствующий `ALLOWED_ORIGINS`.
