# Пошаговый план завершения CRM для ИИ-разработчика

Версия 1.0, 19.09.2026. Цель — довести существующий проект до проверяемой поставки П1 по исходному ТЗ. Это план продолжения разработки, а не задание заново создать CRM.

## 1. Источники, приоритеты и границы

Прочитать в таком порядке:

1. Этот пакет `docs/ai-handoff/` и текущий `README.md`.
2. `docs/source/specification.txt`; оригинальный DOCX из переданного архива при необходимости сверки таблиц.
3. `docs/source/implementation-prompt.txt` как исходные требования к разработке.
4. `docs/open-decisions.md` и актуальный код, миграции, тесты.
5. Прежние `requirements-traceability.md`, `requirements-gap-analysis.md` и OpenAPI — как исторические документы, которые нужно актуализировать, а не как доказательство текущего состояния.

**Действующее решение пользователя:** «пропускай все вопросы реализуй просто как кастомный настраиваемый пользователем». Поэтому неизвестные формулы, ставки, права, шаблоны, правила аналогов, предоплаты и другие бизнес-параметры реализуются настройками с валидацией, версионированием и явным применением. Повторно останавливать всю разработку вопросами В02–В08 нельзя. Неизвестные бизнес-значения нельзя придумывать или выдавать тестовые ставки за реальные.

Статус CONFIGURABLE в старом документе не доказывает наличие работающего редактора и применения настройки. В01 — сведения об исходниках, В12/В13 — в том числе инфраструктура и эксплуатационные обязательства, В15 — границы последующих очередей. Такие сведения не превращаются в выполненные требования от добавления произвольного JSON-поля.

**Объём П1:** F01–F16, XLSX-часть F18, N01–N08, A01–A22. П2: F17 и внешние интеграции F18, фактические расходы/расширенная аналитика. П3: F19 и A24. П2/П3 проектируются с ясными границами, но не реализуются вместо незаконченной П1. УПД, полноценная бухгалтерия, производство, склад по партиям/ячейкам и публичные кабинеты не добавляются в П1.

Сохранить существующий стек. Не заменять FastAPI, PostgreSQL, SQLAlchemy/Alembic, React/TypeScript/Vite и pnpm без доказанного технического препятствия. Не дробить приложение на микросервисы. Исправления делать небольшими, проверяемыми изменениями.

## 2. Организация работы

Каждый этап ниже разделён на задачи, которые удобно выпускать отдельными PR. Один PR закрывает понятный результат: бизнес-правило вместе с API, нужной формой, проверками и документацией. Общую замену всех моделей, API и экранов одним PR не делать.

Для каждой задачи:

1. Записать код требования F/N/A, воспроизводимый исходный сценарий и ожидаемый результат.
2. Найти текущую реализацию; не дублировать уже существующий сервис или маршрут.
3. Для дефекта финансов, доступа или состояния сначала добавить падающий предметный тест.
4. Исправить сервер и необходимые ограничения БД; обновить API и интерфейс в пределах задачи.
5. Выполнить связанные проверки, затем регрессию на контрольной точке этапа.
6. Обновить матрицу требований, журнал дефектов и отчёт с фактическими командами.
7. Сохранить изменения в Git и передать результат в формате `REVIEW-PROTOCOL.md`.

Ветки — по правилам подключённого репозитория; при отсутствии других правил использовать `codex/sNN-short-topic`. Не менять опубликованную историю и не перезаписывать чужую ветку. Если удалённый репозиторий недоступен, подготовить локальный коммит/patch и честно указать это. Не сообщать о созданном PR без его действительной ссылки.

Не тратить весь этап на повторное составление плана. Начать с воспроизведения текущего состояния, затем исправлять конкретный дефект. Отчёт должен содержать файлы, проверки и демонстрируемое изменение, а не только описание намерений.

### Порядок зависимостей

| Группа | Этапы | Что должно появиться |
|---|---|---|
| Воспроизводимая основа | S00 → S01 → S02 | Baseline, CI, миграции и настоящая PostgreSQL-проверка |
| Безопасность и правила | S03 → S04 | Объектные/финансовые права, безопасный повтор, работающие настройки |
| Сделка от клиента до денег | S05 → S06 → S07 → S08 → S09 | CRM, закупки, расчёт, документы, платежи |
| Исполнение сделки | S10 → S11 | Исправляемый согласованный состав, волны и фактическое исполнение |
| Совместная работа и отчёты | S12 → S13 → S14 | Общение, точная аналитика, законченные сценарии интерфейса |
| Эксплуатационные доказательства | S15 → S16 → S17 → S18 | Фоновые операции, восстановление, перенос данных, нагрузка |

S14 не заменяет UI-работу внутри предыдущих этапов. Нельзя откладывать критичный дефект доступа или денег ради косметики: небольшой исправляющий PR допустим раньше своего большого этапа, после появления воспроизводящего теста.

## S00. Принять репозиторий и зафиксировать исходное состояние

**Требования:** N07; доказательства для всей приёмки. **Зависимости:** нет.

1. Проверить ветку, HEAD, незакоммиченные изменения, структуру репозитория и реально переданные файлы. Не предполагать, что состояние равно архиву от 15.09.
2. Зафиксировать точный commit SHA в `docs/baseline.md`. Если история ещё не создана, сохранить исходный снимок отдельным первым коммитом после проверки секретов.
3. Сверить включённые файлы с `SNAPSHOT-MANIFEST.json`, если он передан. Не коммитить `.env`, `.runtime/`, credentials, дампы, `node_modules`, `.venv`, логи и архивы с данными. Дополнить `.gitignore` для `deliverables/` и генерируемого `*.tsbuildinfo`, если эти файлы остаются в рабочей папке.
4. Составить реестр фактических маршрутов и экранов. Отдельно выписать устаревшие документы: старая матрица ещё сообщает «реализация не начата».
5. Запустить доступные baseline-проверки, разделив независимые SQLite-проверки и PostgreSQL. Недоступную проверку пометить NOT_RUN с причиной, а не PASS.
6. Создать `docs/acceptance-report.md`, `docs/defects.md`, `docs/progress.md`. Перенести известные дефекты из READINESS с признаками STATIC_FINDING / REPRODUCED / FIXED / VERIFIED.
7. Сделать минимальный набор обезличенных тестовых пользователей по ролям; реальные локальные учётные записи и пароли в фикстуры не переносить.

**Проверки:** исходные 33 локальных теста и сборка интерфейса; Ruff/Stylelint; список PostgreSQL-тестов; наличие/отсутствие UI-тестов. Старые результаты сравнить с текущими, не подменять ими новые.

**Готово, когда:** другой разработчик понимает точную исходную версию, воспроизводит baseline и видит открытые дефекты. Данные владельца не изменены.

**Передать:** baseline-коммит, отчёт команд, фактическую матрицу требований. Не задерживать следующие работы ради идеального оформления документов.

**Требования:** N07, N02. **Зависимость:** S00.

1. Устранить неиспользуемые импорты и порядок импортов в `backend/tests/test_postgres_commerce.py`.

3. Зафиксировать согласованные команды форматирования, линтинга, TypeScript и тестов; не считать отсутствие файлов тестов успешным тестированием frontend.
4. Добавить реальные frontend-регрессии для API-ошибок, повторяемой команды, сохранения черновика и преобразования дат. Использовать существующий Vitest и Testing Library.
5. Добавить CI для установки по lock-файлам, backend tests, frontend tests, TypeScript, ESLint, Stylelint и сборки.
6. В отдельной CI-задаче запускать PostgreSQL, применять Alembic и выполнять тесты с маркером `postgres`. Отсутствие PostgreSQL в этой задаче должно завершаться ошибкой, а не скрытым skip.
7. Сохранять тестовые отчёты и артефакт сборки. Проверки секретов и зависимостей добавлять с разбором результатов; не обновлять все библиотеки без связи с задачей.

**Готово, когда:** CI зелёный на фактическом коде, каждый обязательный job действительно выполняется, frontend содержит содержательные тесты. Нет правил, глобально отключённых ради зелёного статуса.

**Передать:** workflow, команды локального повторения и ссылку на запуск CI либо локальный эквивалент с честной пометкой.

## S02. Проверить миграции, ограничения и неизменяемую историю

**Требования:** N02, N04, N07; A09–A10, A22. **Зависимость:** S01.

1. Поднимать отдельную тестовую PostgreSQL-базу/схему. Проверить, что тесты никогда не используют `public` рабочей CRM. Исполнять настоящие миграции, как уже делает текущий PostgreSQL fixture.
2. Проверить `2abdec759d06_initial_schema` на пустой базе, затем `51eab019a784_protect_history` на базе с историческими документами, квотами, оплатами и аудитом.
3. Для каждой защищённой таблицы проверить прямые UPDATE/DELETE/TRUNCATE. Запрещённые изменения исторических фактов должны отклоняться; разрешённые поля жизненного цикла — изменяться.
4. Пройти через API выпуск документа, отметку отправки, решение согласования, подтверждение оплаты, отмену планового распределения. Триггеры не должны ломать эти разрешённые действия.
5. Убрать из PostgreSQL-фикстур прямое редактирование immutable-квот. Формировать новые редакции штатными командами. Быстрые SQLite-тесты не использовать как доказательство поведения триггеров.
6. Проверить внешние ключи, unique/check-ограничения, циклические зависимости, Decimal precision, nullability и индексы по фактическим запросам. Выполнить `alembic check`.
7. Разделить PostgreSQL-роли: владелец/миграции, API/worker, резервирование. Runtime-процесс не владеет схемой и не может отключить триггеры, менять audit или выполнять DDL. Миграции используют отдельные credentials.
8. Протестировать обновление с данными и план отката. Если downgrade разрушителен, явно задокументировать восстановление предыдущего релиза из копии; не обещать безопасный downgrade любой ценой.
9. Не переписывать уже применённые миграции. Исправления оформлять новой ревизией и сохранять путь обновления существующей базы.

**Готово, когда:** повторно проходят шесть текущих конкурентных тестов на мигрированной PostgreSQL, отдельные тесты триггеров и ролей, обновление сохраняет снимки/файлы/балансы.

**Передать:** протокол миграций с версиями до/после, SQL-права ролей без секретов, команды повторения и доказательство, что рабочие данные не затронуты.

## S03. Закрыть нарушения доступа и безопасно повторять команды

**Требования:** F01, F16, N02–N04, A20–A21. **Зависимость:** S02.

1. Ввести единый способ проверить разрешение **на конкретный объект**. Наличие `finance.purchase.read` ещё не означает доступ к закупке всех заявок. Проверять own/shared/all для каждого финансового разрешения.
2. Разделить DTO/проекции закупки, детального расчёта, вознаграждений, планового результата и клиентских итогов. Скрывать поля до отправки JSON, не CSS-стилем в браузере.
3. Исправить `quote_view`, `calculation_view`, выдачу профилей и истории. Список профилей не должен раскрывать закрытые коэффициенты/вознаграждения обладателю другого финансового разрешения.
4. Исправить `payment_view`: сведения о связанных счетах и распределениях должны учитывать доступ к каждой связанной заявке. Допустимые агрегаты и ссылки определить явно и проверить, что по ним нельзя восстановить закрытые суммы.
5. Изменить повтор `idem`: сохранять идентичность и бизнес-результат операции, но выдавать результат по актуальным правам. Старый ключ не должен возвращать сохранённый секретный JSON после отзыва разрешения. Повтор не создаёт вторую операцию; иной payload с тем же ключом даёт 409.
6. Применить одинаковые правила видимости задач в `/tasks`, dashboard, `request_detail.next_task` и уведомлениях. Отсутствие `tasks.read` не эквивалентно `own`. Учесть отзыв доступа к объекту задачи и own-scope волн.
7. Проверить прямые URL, экспорты, документы, историю, списки, поисковые подсказки, чат/document_refs и вложения. Ссылка не расширяет права исходного документа.
8. Проверить блокировку пользователя, отзыв роли, персональный deny при нескольких ролях, смену пароля, истечение сессии, CSRF и MFA на реальном auth-пути без подмены `current_user`.
9. Проверить, что логи, ошибки, метрики, audit и metadata фоновых заданий не содержат пароли, токены и закрытые бизнес-значения.
10. Обновить UI: показывать разрешённые действия, объяснять недоступность; сервер остаётся источником разрешений. Изменение прав в активном сеансе должно корректно обновлять интерфейс.

**Обязательные тесты:** `requests.read=all + purchase=own`; повтор сохранённого расчёта после отзыва reward; платёж A со связанным счётом B; личный чат руководителю без членства; revoked session; task leaks через dashboard/next_task; каждый вариант own/shared/all + deny.

**Готово, когда:** тесты воспроизводят прежние утечки, после исправления закрытые значения отсутствуют на всех проверенных путях, а разрешённая работа сохраняется.

**Передать:** `docs/permissions.md`, матрицу негативных сценариев и результаты тестов на точном SHA.

## S04. Превратить «настраиваемость» в работающие правила

**Требования:** решение пользователя по В01–В15; F01, F03, F07–F14, F16. **Зависимости:** S02–S03.

1. Создать реестр типов настроек: область применения, схема, допустимые значения, автор, версия, дата действия, права редактирования и история.
2. Разделить черновик, проверку и публикацию бизнес-профиля. Финансовые документы ссылаются на опубликованную версию; изменение настроек не пересчитывает старые операции.
3. Финансовые профили: валюты, формулы/базы, точность, округление, затраты, налоговые категории, порог цены/финансирования, вознаграждение с точным названием и основанием.
4. Коммерческие правила: частичное принятие, аналоги, упаковки/кратность, несколько поставщиков, исключения по предоплате, критерий продажи и закрытия, нумерация и печатные шаблоны.
5. Справочники: результаты звонка и причины потерь, химические характеристики/категории, обязательные паспорта, признаки перевозки, календарь/праздники, часовой пояс, история группового чата и ограничения файлов.
6. Каждая настройка должна реально влиять на серверное поведение. Неподдержанный вариант отклонять понятной ошибкой, не заменять незаметно стандартным правилом.
7. Сделать обычные формы для ключевых настроек и эффективных прав. JSON оставить как дополнительный экспертный режим с валидацией и предпросмотром, а не единственный способ настройки компании.
8. Для нового пустого окружения создать мастер заполнения организации и правил. Пока обязательный параметр не заполнен, блокировать только зависимую операцию и объяснять, где его указать.
9. Демонстрационные профили помечать тестовыми. Не активировать реальные налоговые ставки, формулы и реквизиты автоматически.

**Проверки:** один пользователь публикует две версии правила; старый документ не меняется, новый использует новую версию. Неуполномоченный сотрудник не публикует профиль. Некорректное правило не попадает в рабочее состояние.

**Готово, когда:** В-вопросы представлены конкретной настройкой/документированной внешней зависимостью с проверкой применения. Повторных вопросов владельцу для продолжения кодирования не требуется.

## S05. Довести клиентов, импорт, обзвон, задачи и позиции заявки

**Требования:** F02–F04, F15, XLSX F18; A01–A02, A10. **Зависимости:** S03–S04.

1. Согласовать create/PATCH-схемы: различать пропущенное поле и явный null; не очищать обязательные поля. Все количества передавать Decimal-строками, все моменты времени — с часовым поясом.
2. Исправить изменение продавца: после выпуска документа нельзя обойти правило через `seller_id=null`. Определить архивирование клиента/позиции со связанными объектами без удаления истории.
3. Реализовать полный цикл контакта: просмотр, создание, исправление и архивирование; формы выбора используют имена и серверный поиск, а не ручной UUID.
4. Проверить импорт на 100 строках: 90 созданий, 5 обновлений внешнего ID, 5 ошибок; источник и звонки существующих клиентов сохраняются. Повтор подтверждения и повтор обработки не создают дублей.
5. Проверить сопоставление колонок, формулы/макросы, leading zeros, длины, email/phone, конфликт внешнего ID, чужого владельца, ошибки строки и файл ошибок. При неоднозначном совпадении — явное решение.
6. Полностью пройти `ImportDialog`: две и более страницы, сохранение решений при навигации, queued/completed/failed, закрытие/повторное открытие, история партий. Не показывать успех, пока worker не завершил запись.

## S06. Закончить каталог, запросы поставщикам и квоты

**Требования:** F05–F07; A03–A07. **Зависимости:** S05.

1. Провести A03 буквально: три позиции в заявке, выбраны две, в XLSX ровно две и только разрешённые поля. Снимок, hash и автор сохранены; скачивание не отмечает отправку.

10. UI сравнения: варианты рядом, отличия от потребности, число упаковок, срок, доступность и только разрешённые цены. Если есть общий подтверждённый лимит поставщика — контролировать суммарный расход; без лимита не обещать резерв.

**Готово, когда:** A03–A07 выполняются на реальных маршрутах и UI, включая конкурентное создание и отсутствие закрытых полей в экспортируемом RFQ.

## S07. Довести финансовое ядро и версии расчётов

**Требования:** F08–F09, N02; A05–A10. **Зависимости:** S04, S06.

1. Описать в `docs/calculations.md` входы, единицы, формулы, порядок округления, расходы, налоговые категории, выходы и версию алгоритма. Сервер — единственный источник итоговых чисел.
2. Проверить арифметику без float на всём пути UI→API→DB→snapshot→PDF/XLSX. Количество до 6 знаков, курсы/коэффициенты до 8 — проверяемая политика, не неявное округление.
3. Проверить ограниченный интерпретатор: запрещены вызовы, атрибуты, импорт, бесконечные/огромные выражения, NaN/Infinity, деление на ноль и неизвестные переменные. Ошибки связывать с конкретной формулой.
4. Валюта квоты, управленческая и продажи хранятся отдельно. Курс содержит направление, число котируемых единиц, дату, источник, автора и причину. Старый курс остаётся в snapshot.
5. По умолчанию П1 один поставщик и одна исходная валюта на КП. UI объясняет конфликт и предлагает группы, сервер проверяет повторно. Другой разрешённый режим возможен лишь как явная проверенная политика, а не случайное снятие проверки.
6. Расходы: стоимость/масса/объём/ручное распределение, явная база, включение в cost/cash, точный остаток по постоянному ID. Нулевая база — ошибка с выбором другого метода.
7. Добавить налоговую категорию, ставку/освобождение, базу и сумму каждой строки; отдельные итоги категорий. Сейчас единой `profile.tax_category` недостаточно для смешанного документа.
8. Разделить себестоимость, денежную потребность, наценку, маржу, вознаграждение и плановый результат. Поддержать отключённое вознаграждение и заданные пользователем базу/название/право доступа.
9. Порог цены и исключение оформить полномочием/основанием и аудитом. Не подменять специфическую пошлину процентом, если профиль её не поддерживает.
10. Повторно считать сервером при сохранении. Изменившиеся request/quote/profile версии вызывают конфликт без записи неправильного результата.
11. Сохранять полный immutable snapshot и идентификатор версии алгоритма. Добавить сравнение версий по смысловым полям, не только вывод JSON.
12. Довести живой preview с отменой устаревших запросов, видимым признаком «не записано», общим и подробным режимами по правам. В UI добавить ручное распределение и другие реально поддержанные сервером варианты.

**Обязательные проверки:** A08 даёт cost=2500, cash_need=2731, total=3593.75; 0.1+0.2=0.3; разные точности/валюты; нулевые базы; смешанные налоги; фиксированный seed генеративных проверок сумм; 100 строк; тот же snapshot после изменения справочников.

**Готово, когда:** нет необъяснимой разницы preview/save/document, набор синтетических контрольных профилей воспроизводим. Реальные примеры владельца подключаются отдельной проверкой профиля компании; их отсутствие не останавливает разработку универсального ядра.

## S08. Исправить принятие состава, выпуск КП и счетов

**Требования:** F10; A07, A09–A12. **Зависимости:** S05–S07.

1. Сначала воспроизвести `partial_amount`: net=0.02, quantity=4, четыре принятия по 1. Исправить распределение округления по накопленной доле либо другим доказанным методом: каждая часть неотрицательна, сумма частей равна источнику.
2. Проверить отдельно net, tax и total, частичное принятие и частичные счета; разные способы округления и сотни частей. Повтор команды не перераспределяет уже зафиксированные копейки.
3. На принятии повторно проверять упаковки, кратность, MOQ и единицы. Расчёт 100 г в упаковках 25 г не даёт права принять 1 г при неделимой упаковке.
4. Принятие альтернатив суммировать по одной потребности в общей единице с учётом корректировок/отмен. Клиентское решение по аналогу привязывать к точной редакции.
5. Счёт — одна организация, один клиент, одна валюта и одно принятое КП. Проверять уже выставленный состав; авансовые/окончательные режимы не подменять повторным полным счётом.
6. Создать типизированные настраиваемые реквизиты/шаблоны: контакт, цена единицы, сумма, налоги по категориям, сроки/условия поставки и оплаты, CAS/производитель по настройке. Не печатать Python/JSON-словарь реквизитов как текст.
7. Перед выпуском проверять обязательные реквизиты шаблона. Все выпущенные значения, версия шаблона и байты файлов фиксируются.
8. PDF и XLSX формировать из одного snapshot. Проверить кириллицу, длинные названия химических продуктов, переносы, 100 строк, шапку/нумерацию страниц, клиентские итоги и отсутствие внутренней экономики.
9. Включить доступный Unicode-шрифт и его лицензию в контейнер. Проверить именно контейнерную генерацию, не системный Arial на компьютере разработчика.
10. Нумерация уникальна по продавцу/виду/периоду. Провести одновременный выпуск, повтор после потери ответа и повторное скачивание с тем же SHA-256.
11. Отметка отправки отдельна от скачивания. Изменение отправленного/оплаченного документа — новая версия или отдельная аудируемая отмена с финансовыми последствиями.
12. Собрать дерево связей заявки: позиция → RFQ/квота → расчёт → КП → принятый состав → счёт → платёж → согласование → волна. Переходы работают по одной идентичности объекта.

**Готово, когда:** A09–A12 и крайний пример округления проходят; файлы и старые ссылки не меняются при редактировании клиента, шаблона, квоты или курса.

## S09. Проверить весь журнал оплат и его последствия

**Требования:** F11, N02; A13–A15, A20. **Зависимости:** S03, S08.

1. Заявление об оплате не уменьшает долг. Подтверждение выполняется с отдельным правом; автор заявления и контролёр сохраняются раздельно.
2. Проверить распределение между несколькими счетами одного клиента/продавца/валюты. Ограничения суммы платежа и остатка счёта защищены конкурентными транзакциями.
3. Дубликат по внешнему ID блокируется; совпадения без ID показываются для разбора, не объявляются автоматически дублем только из-за одинаковой суммы.
4. Нераспределённый остаток показывается авансом. Валюты не смешиваются. Отрицательная задолженность не используется для маскировки переплаты.
5. Разделить refund, снятие распределения и исправление. Обратные операции сохраняют первоисточник, причину, автора и идемпотентность. Историю не редактировать и не удалять.
6. Создать единый пересчёт финансирования всех затронутых исполнений после любого изменения ledger. Дефицит должен не только появляться при отмене, но и исчезать при восстановлении покрытия.
7. Получателей уведомлений определять по фактическим затронутым заявкам, включая счёт другой заявки в одном платеже. Уже отправленное количество не отменять из-за возврата денег.
8. UI показывает заявлено/подтверждено/распределено/возвращено/аванс/долг, валюту, историю и связи; суммы согласуются с сервером и правами.

**Проверки:** A13–A15; две оплаты на один остаток; два распределения одного платежа; повтор ключа/потерянный ответ; refund после allocation; полная цепочка approve → unallocate → дополнительное финансирование; несколько заявок и отозванные права.

**Готово, когда:** для каждого контрольного набора объяснимо балансовое равенство, нет переприсвоения денег или ошибочно сохраняющегося дефицита.

## S10. Реализовать исправление принятого состава и полное согласование

**Требования:** F10–F12; A11, A15–A16. **Зависимости:** S08–S09.

1. Описать отдельные команды отмены и новой редакции принятого исполнения: причина, исходная версия, новый состав, отношения со счетами, оплатами, волнами и фактическими событиями.
2. Не решать задачу свободным PATCH `Execution.snapshot`. Исторический принятый состав остаётся фактом; текущие активные количества и связи вычисляются из явных операций/версий.
3. Если есть выставленный/оплаченный счёт, исправление требует согласованного финансового пути. Физически отправленный товар нельзя тихо заменить другой квотой или поставщиком.
4. Перед отправкой на согласование проверить точную редакцию, доступность квот/характеристик, количество и покрытие по опубликованному профилю. Повтор не создаёт вторую задачу руководителю.
5. Руководитель видит состав, доступное финансирование, сроки и предупреждения. Возврат/отклонение требуют комментария; решение подписывает точный snapshot/digest.
6. Повторить A16 буквально: руководитель возвращает; меняется поставщик/состав; создаётся новая редакция и новое согласование. Старое решение нельзя использовать для нового распределения.
7. Защитить конкурирующие решения, изменение состава во время решения и повтор после потери ответа. Конфликт не уничтожает ранее сохранённое решение.
8. UI предоставляет очередь согласований, просмотр состава, возврат, исправление и повторную отправку. Поля revision/cancelled_quantity в БД сами по себе не считаются готовой функцией.

**Готово, когда:** полный A16 работает через UI/API, сохраняет предыдущую историю и финансовые последствия. Существующий тест, повторно согласующий неизменённый состав, дополнен настоящей сменой состава.

## S11. Довести волны, фактическое исполнение и состояния заявки

**Требования:** F13, независимые состояния раздела 5; A17–A18. **Зависимость:** S10.

1. Формализовать независимые коммерческое, финансовое и исполнительское состояния в `docs/states.md`. Не пытаться одним полем stage заменить все процессы.
2. Согласованный объём распределять по открытым волнам транзакционно. Пример 10 → 6+4 допустим; ещё 1 — нет. Совместимые единицы приводятся явно.
3. Для переноса учитывать актуальные нетто-факты и причину. Сейчас наличие любого исторического события блокирует перенос даже после полной корректировки; устранить противоречие текста ошибки и поведения.
4. Отправленное количество не переносить как плановое. Отмена плановой волны освобождает остаток; отправленная волна не отменяется с удалением движения.
5. События ordered/ready/shipped/arrived/delivered и претензии имеют фактическое количество, дату, автора, документ. Исправление — отдельное событие с ссылкой на исходное.
6. После корректировки вниз или открытия претензии в completed-волне итог должен пересчитываться или явно переоткрываться по правилу. Статус completed при недоставленном остатке не оставлять.
7. Проверить финансирование после reversals, запрет нового запуска при дефиците и сохранение уже совершённых фактов.
8. Изменение дат волны обновляет прогноз и уведомляет менеджеров; клиентское обещание сохраняется отдельно. Добавить плановые/фактические даты, вложения и обсуждение волны.
9. Поддержать настраиваемые плановые расходы волны и распределение; фактическую себестоимость П2 не выдавать за уже реализованную.

11. Реализовать успешное коммерческое закрытие и переоткрытие заявки. Сейчас `closed_at` устанавливается только для проигранной заявки. Принятие 6 из 10 не завершает оставшуюся потребность без явного решения о ней.

**Проверки:** 6 доставлено + 4 перенесено; transfer одновременно с ship; completed → корректировка/претензия; отмена плановой волны; частичная продажа и остаток; отсутствие отрицательных/дублируемых количеств.

**Готово, когда:** A17/A18 проходят, сумма распределений/фактов соответствует согласованному составу, коммерческое закрытие и исполнение не подменяют друг друга.

## S14. Завершить интерфейс сквозного процесса

**Требования:** раздел 14.1, F01–F16, N01–N03. **Зависимости:** предыдущие функциональные этапы.

**Готово, когда:** пользователь с каждой ролью выполняет свою часть сделки без консоли разработчика и ручного SQL. Скриншоты дополняют, но не заменяют проверки сохранённых данных.

## S15. Доказать надёжность очереди, файлов и наблюдаемости

**Требования:** N02, N05, F15–F16; A21–A22. **Зависимости:** S02, S12.

1. Проверить текущие `core/jobs.py` и worker: retry, backoff, terminal failure, версия, безопасная ошибка, восстановление ImportBatch/FileRecord, одно уведомление по событию.
2. Испытать два worker на PostgreSQL с SKIP LOCKED. Убить один в процессе операции; после перезапуска не должно быть частично записанного импорта или дублированного эффекта.
3. Проверить потерю HTTP-ответа после commit и повтор клиента с прежним ключом. Не путать повтор запроса с повторным выполнением бизнес-операции.
4. Проверить сбои БД, scanner, файловой системы и генерации. Документ не должен ссылаться на недописанный файл; временные/осиротевшие файлы убираются по доказанной безопасной процедуре.
5. Для долгих операций обеспечить сохранённое состояние, корреляцию с бизнес-объектом, реальный прогресс или честный статус. Если PDF/экспорт синхронны и не укладываются в цели, вынести в идемпотентный job.

7. Настроить защищённый путь сбора метрик; существующий loopback-only `/metrics` сам по себе не подключает мониторинг.

**Готово, когда:** сбой процесса и повторная обработка проверены фактически, ошибки наблюдаемы, основной просмотр CRM сохраняется при отказе вспомогательного сервиса.

## S16. Реализовать резервирование и проверить восстановление

**Требования:** N06, N05, A22. **Зависимости:** S02, S15; работу начать раньше завершения всей функциональности.

1. Реализовать отсутствующий `scripts/recovery.py` либо заменить оболочки завершённым согласованным инструментом. Ни одной команды, ссылающейся на несуществующий обработчик, в поставке не оставлять.
2. Определить комплект копии: PostgreSQL, все связанные приватные файлы/версии документов, версия приложения/миграции, безопасная конфигурация и отдельная процедура восстановления ключей.
3. Добиться согласованности БД и файлов. Для первого учебного восстановления допустима короткая явно описанная остановка записи. Рабочая стратегия должна отдельно доказать заявленные RPO и доступность; ежедневного dump недостаточно для RPO=1 час.
4. Выбрать и реализовать стратегию частых согласованных копий либо WAL/PITR с версионированными файлами. Не объявлять PITR файловой части только на основании наличия WAL базы.
5. Каждая копия имеет идентификатор, время контрольной точки, версии, manifest, hashes и результат проверки. Backup не попадает в обычные файлы/экспорт CRM.
6. Отдельное хранилище и полномочия, шифрование, расписание, retention и уведомление о просроченной/неудачной копии. Исходные цели ТЗ: потеря не более часа, восстановление до четырёх часов; ежедневные точки 30 дней и частые за сутки — настраиваемый профиль.
7. Restore по умолчанию создаёт новую изолированную среду. Не удаляет существующие volumes и не перезаписывает рабочую БД без отдельной явной команды с указанием цели.
8. Выполнить настоящий backup → restore с заявкой, редакциями, расчётом, КП, счётом, платежом, reversal, approval, wave, chat и файлами.
9. Проверить количества записей/связи, балансы отдельно по валютам, неизменность snapshot/hash, возможность открыть/скачать документы, работу новых операций и действующие права после восстановления.
10. Измерить фактические RPO/RTO на указанном объёме. Повредить тестовую копию/удалить тестовый файл: проверка должна обнаружить неполноту, а не дать зелёный отчёт.
11. Документировать периодическое учебное восстановление, владельца процесса, восстановление доступа и ключей. Отсутствующие внешние credentials обозначить как зависимость эксплуатации, но сами команды и тестовый стенд завершить автономно.

**Готово, когда:** существует протокол фактического восстановления в отдельную среду; ZIP/dump без проверки не считается выполнением N06.

## S17. Подготовить перенос существующих данных

**Требования:** N08; миграционная часть A22. **Зависимости:** S05, S08, S16.

1. Создать шаблон реестра источников: файл/система, сущности, владелец колонок, внешний ID, контрольное число, источник истины и стратегия обновления.
2. Реализовать dry-run переноса с отчётом ошибок/дублей/сопоставлений, контрольными суммами по валютам и ссылкой каждой импортированной записи на источник.
3. Разделить структурированный перенос и исторический архив. Старый расчёт без исходных формул/курсов пометить архивным; не пересчитывать его новым профилем и не объявлять восстановленной версией.
4. Подготовить синтетический представительный набор, включая старые документы, валюты, дубликаты, отсутствующие поля и исторических сотрудников.
5. Пробный перенос повторяем, не создаёт дублей и имеет отчёт расхождений. Ошибка не оставляет неясную половину применённых финансовых операций.
6. Описать freeze/delta перед окончательным переключением, сверку контрольных чисел и возможность возврата к источникам.
7. Реальные исходные файлы/прототип могут отсутствовать. Подготовить инструмент и шаблон отчёта, отметить `WAITING_FOR_SOURCE_DATA` только для проверки реального переноса; остальные этапы не блокировать.

**Готово, когда:** технический инструмент и контрольный перенос проверены; финальный перенос реальных данных имеет отдельный протокол, когда владелец их предоставит.

4. Отдельно пройти негативные ветки: чужие права/файл/чат, старый ключ после отзыва права, конфликт версии, просроченная квота, несогласованный аналог, дробное округление, возврат денег, изменение состава после возврата руководителя, сбой worker и восстановление.
5. Приложить доказательства A22: backup/restore, нагрузка, обновление/откат и контрольный перенос. Проверки на синтетике отделить от пилота компании и реальной миграции.
6. Блокирующие дефекты денег, количества, доступа, истории, восстановления или основного процесса должны быть закрыты. Остальные замечания перечислить явно; не уменьшать объём молча.
7. Подготовить пользовательскую инструкцию и демонстрацию для менеджера/руководителя. Реальный пилот и формальное принятие отмечает владелец, а не ИИ за него.
8. Передать исходники с историей Git, release tag, миграции, зависимости, шаблоны/профили, тестовые данные, OpenAPI, эксплуатационные инструкции и протокол приёмки.

**Готово, когда:** все обязательные технические критерии доказаны, внешние условия пилота/эксплуатации обозначены отдельно и владелец может принять конкретную поставку. «Все тесты зелёные» без перечня проверенных требований недостаточно.

## 4. Что делать после П1

П2 оформляется отдельным планом по выбранным владельцем интеграциям. Для F17 сначала определить достоверные начальные остатки, начисления, оплаты и возвраты; счёт сам по себе не создаёт оборот сверки. Для обменов F18 — внешний ID, источник истины поля, журнал, retries и контроль дублей. A23 проверяет достоверность и блокировку окончательной формы при неполноте.

П3 — аналитический помощник только для чтения через ограниченный API с правами текущего пользователя. Резервные копии не служат источником для модели. Ответы содержат период, фильтры, источники и ссылки; числа рассчитывает сервер. Выбор провайдера/ключей/бюджета и передачи данных выполняется при отдельном подключении. A24 проверяет точность, запреты и игнорирование инструкций в пользовательских текстах. Отказ помощника не блокирует CRM.
