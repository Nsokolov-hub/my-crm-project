# Инструкция по развертыванию (Deployment Guide)

Это техническая справка. Для первого запуска с пояснениями по каждому шагу используйте [локальную инструкцию](install-local-docker.md) или [инструкцию для VPS](install-hosting-vps.md).

## 1. Требования
* Docker 24.0+
* Docker Compose v2.20+
* Оперативная память: от 4 ГБ (ClamAV потребляет около 2 ГБ ОЗУ)
* Свободное дисковое пространство: от 10 ГБ

## 2. Первоначальный запуск (Clean Installation)

Склонируйте репозиторий в чистую директорию.

1. Сгенерируйте приватный `.env` файл со случайными паролями и ключами:
```bash
python3 scripts/init-env.py --database crm
```
Скрипт создаст `.env` с правами `0600`, сгенерирует независимые криптографические ключи и пароли для ролей `POSTGRES_PASSWORD`, `CRM_API_PASSWORD` и `CRM_BACKUP_PASSWORD`.

2. Запустите стек сервисов:
```bash
docker compose build api web
docker compose up -d --no-build
```
> **Внимание:** Сервис `migrate` перед миграциями Alembic автоматически инициализирует и актуализирует ограниченные роли `crm_api` (только DML) и `crm_backup` (только SELECT).
> ClamAV инициализируется около 180 секунд для загрузки антивирусных баз. Сервисы `api` и `worker` запустятся под ограниченной ролью `crm_api` после завершения миграций.

3. Проверьте `docker compose ps -a`: `migrate` должен завершиться с кодом `0`, а `db`, `clamav`, `api` и `web` — стать `healthy`. Затем создайте первого владельца CRM; пароль длиной от 12 символов будет запрошен в терминале:
```bash
docker compose exec api python -m app.bootstrap --email owner@example.com --name 'Владелец' --all-roles
```
Интерфейс доступен по адресу <http://127.0.0.1:8080/>. Используйте собственный адрес почты вместо примера. Если меняете внешний веб-порт `8080`, включите фактический адрес браузера в `ALLOWED_ORIGINS` файла `.env` и пересоздайте контейнер `api`.

## 3. Разделение сред и безопасность ролей (Dev / Test / Prod)

* **Ролевая изоляция БД:**
  * Сервисы `api` и `worker` подключаются под ограниченной ролью `crm_api`, не имеющей прав DDL (`DROP TABLE`, `ALTER TABLE` заблокированы на уровне СУБД).
  * Резервное копирование выполняется под ролью `crm_backup` (доступ только на чтение, запись заблокирована).
  * Миграции схемы выполняются выделенным сервисом `migrate` под учетной записью владельца БД.
* **Защита неизменяемой истории:** Все финансовые и аудиторные таблицы защищены триггерами `crm_protect_history()`, блокирующими `UPDATE` и `DELETE`.
* **Сетевая изоляция:** Порты `db`, `clamav`, `api` и `web` в стандартном Compose привязаны только к `127.0.0.1` компьютера запуска. Для доступа извне отдельно настройте HTTPS-прокси и разрешённый источник браузера в `ALLOWED_ORIGINS`.

## 4. Обновление (Update)

Для обновления продукта до новой версии выполните:
```bash
git pull origin main
docker compose build api web
docker compose up -d --no-build
```
Миграции базы данных и обновление прав ограниченных ролей запустятся автоматически сервисом `migrate` до старта API.

Если после обновления интерфейс открывается, но создание организации или сотрудника не сохраняется, проверьте запрос в инструментах браузера: вкладка **Network → Fetch/XHR**, затем нажмите **Сохранить**. В актуальной версии должен появиться `POST /api/v1/sellers` либо `POST /api/v1/admin/users` с ответом `201`. Если POST отсутствует, обновите веб-образ командами выше и перезагрузите страницу браузера. Если POST возвращает `403 ORIGIN_FORBIDDEN`, добавьте точный адрес страницы (протокол, IP/имя и порт) в `ALLOWED_ORIGINS`, затем примените конфигурацию:

```bash
docker compose up -d --no-build --force-recreate api
docker compose exec api printenv ALLOWED_ORIGINS
```

Изменение `.env` само по себе не меняет окружение уже работающего контейнера. При `403 CSRF_INVALID` обновите страницу и войдите повторно. Для этих действий не удаляйте Docker volumes: в них находятся данные компании.

## 5. Резервное копирование и восстановление (Backup & Restore)

Утилита `scripts/recovery.py` (или обёртки `scripts/backup.sh` и `scripts/restore.sh`) сохраняет дамп БД и архив файлов, проверяет их контрольные суммы и защищает распаковку от небезопасных путей. БД и файлы копируются **последовательно**: для согласованной рабочей копии на время резервирования остановите запись через интерфейс и фоновые операции либо проведите его в заранее объявленное окно обслуживания.

### Создание резервной копии
```bash
./scripts/backup.sh --mode docker --compose-storage --retention 7
```
* Создаёт архив `backups/backup_<TIMESTAMP>.tar.gz`.
* Включает дамп БД в кастомном бинарном формате `pg_dump -Fc` и архив файлового хранилища.
* Формирует `manifest.json` с версией, датой, SHA-256 дампа и архива файлов. Пофайловые хеши записываются только при резервировании файлов с диска хоста, не из Docker volume.
* Параметр `--retention 7` автоматически удаляет устаревшие копии, сохраняя 7 последних.

### Восстановление из резервной копии
```bash
./scripts/restore.sh backups/backup_<TIMESTAMP>.tar.gz --force --mode docker --compose-storage
```
* Флаг `--force` обязателен для предотвращения случайной перезаписи данных.
* Перед восстановлением проверяются контрольные суммы всех компонентов по манифесту (при несовпадении процедура прерывается без изменения БД).
* В Docker-режиме перед восстановлением проверяется хеш архива файлов; пофайловая сверка после распаковки доступна только в режиме хранения файлов на диске хоста. После Docker-восстановления проверьте вложение через CRM.
* Выводится фактическое время восстановления (RTO).

## 6. Откат версии (Rollback)

В случае необходимости отката:
1. Восстановите согласованное состояние БД и файлов из бэкапа перед обновлением:
```bash
./scripts/restore.sh backups/backup_<TIMESTAMP_BEFORE_UPDATE>.tar.gz --force --mode docker --compose-storage
```
2. Переключитесь на целевую ветку/тег:
```bash
git checkout <target_tag>
```
3. Пересоберите и перезапустите контейнеры:
```bash
docker compose build api web
docker compose up -d --no-build
```
