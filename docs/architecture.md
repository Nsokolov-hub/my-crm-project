# Архитектура

Модульный монолит FastAPI + SQLAlchemy 2 + PostgreSQL 17. Клиент React/TypeScript/Vite/SCSS, pnpm. Транзакция охватывает команду, аудит, outbox и ключ идемпотентности. UUID — технические ключи; номера отдельные. Чтение и команды проверяют права на сервере. Денежные значения Decimal/Numeric и десятичные строки JSON.

Модули: core (сессии/RBAC/аудит/идемпотентность), crm (контрагенты/контакты/обзвон/задачи/заявки/редакции/импорт), commerce (каталог/квоты/формулы/расчёты/документы/платежи/согласования/волны), communication (чаты/файлы/уведомления), analytics (серверные агрегаты), infrastructure (worker/миграции/резервирование).

Серверная сессия: случайный токен, в БД только SHA-256; HttpOnly cookie, CSRF-токен, SameSite Strict. Роли проверяются при каждом запросе. Администратор не получает финансовых прав автоматически. Персональный deny имеет приоритет над ролями. Для production привилегированным пользователям нужен TOTP. Нет открытой регистрации.

Конкурентные команды блокируют стабильный родительский объект FOR UPDATE; idempotency использует транзакционную advisory-блокировку PostgreSQL. Изменение старой version возвращает 409. Все чтения страниц имеют лимит. Файлы в приватном хранилище; скачивание только через проверку объекта. Внешние файлы изолируются до антивирусного сканирования.

Формулы — ограниченный язык арифметических выражений над Decimal, без Python eval и доступа к объектам/функциям/системе. Пользователь публикует версию профиля; параметры и результаты входят в неизменяемый снимок. Начальных реальных налоговых ставок нет. Условный профиль ТЗ существует только как явно тестовые данные.

П2 и П3 отделены контрактами; интеграции не включаются без подключения и настройки. УПД отсутствует.

## Устройство backend

Каждый пакет (`core`, `crm`, `commerce`, `business`, `communication`, `analytics`, `audit`) делится на модули поддоменов. Например, в `crm` это `catalogue`, `counterparties`, `activities`, `requests` и `quotes`, а общие проверки лежат в `crm/common.py`. Модуль поддомена содержит эндпоинты и функции, которыми пользуются другие модули. `routes.py` пакета только собирает роутеры поддоменов, и подключает его один `app.main`.

Правила проверяет `backend/tests/core/test_architecture.py`:

- обработчик HTTP-запроса не импортируется и не вызывается как функция: общая работа вынесена в обычные функции, например `communication.attachments.attach_file` или `crm.quotes.record_quote_sheet`;
- `routes.py` пакета импортирует только `app.main`, помощники берутся из модуля, которому они принадлежат.

Ответы, у которых есть модель (`response_model`), попадают в `docs/openapi.json` со схемой. Фронтенд берёт из него типы `frontend/src/lib/api-schema.d.ts`, а CI проверяет, что код, документ и типы совпадают. Пока модели есть у сессии и у пользователей (`core.schemas`).

Общие основы лежат в `core`: базовая схема запроса `core.schemas.Input`, параметры эндпоинтов `core.db.DB` (сессия запроса) и `core.security.Actor` (пользователь).

## Живые обновления

Открытые страницы узнают об изменениях из потока событий `GET /api/v1/events` (server-sent events) и сразу перезапрашивают нужные данные: счётчики уведомлений и чатов, открытый чат, статус проверки файлов.

- Команда публикует событие (`core.events.publish`) в своей транзакции. PostgreSQL доставляет `NOTIFY` только после фиксации, поэтому откатившееся изменение страницу не обновляет.
- Каждый процесс API держит одно соединение `LISTEN`. Событие называет пользователей, вид и идентификаторы объектов, но не содержимое: данные страница перечитывает обычными запросами с проверкой прав.
- Опрос сервера остаётся запасным вариантом: при подключённом потоке он идёт в шесть раз реже, в скрытой вкладке не идёт совсем.
- После переподключения страница перечитывает всё, что могла пропустить.

## Параллельные модели

Часть предметной области существует в двух вариантах. Удалять старый вариант можно только после проверки рабочих данных.

| Область | Текущая модель | Ранняя модель | Состояние |
|---|---|---|---|
| Квоты поставщиков | `QuoteSheet` / `QuoteItem` (`crm.quotes`) | `Quote` (`commerce.procurement`) | Интерфейс читает и создаёт только листы квот. Создание и пересмотр ранних квот (`POST /requests/{id}/quotes`, `POST /quotes/{id}/revise`) помечены в API как устаревшие. |
| Каталог | `Nomenclature` / `Packing` / `ProductGroup` | `Product` / `Substance` / `Manufacturer` | Ранний каталог ещё показывается и подтверждается на странице «Каталог». |
| Методика расчёта | `itemized-v2` (`commerce.itemized`) | формульные профили `decimal-dsl-1` (`commerce.calculator`) | Формульный расчёт работает только с ранними квотами. |
| Согласования | `WorkflowReview` (`/workflow-approvals`: платежи, расчёты, задачи) | — | `Approval` (`/approvals`) — отдельная действующая функция: руководитель согласует исполнения заявки. |

Технические ориентиры: [FastAPI Docker](https://fastapi.tiangolo.com/deployment/docker/), [SQLAlchemy versioning](https://docs.sqlalchemy.org/en/20/orm/versioning.html).
