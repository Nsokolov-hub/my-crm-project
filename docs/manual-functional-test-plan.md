# План ручного функционального тестирования «Реактив CRM»

**Назначение:** приёмка базовой CRM небольшой компании на чистом тестовом стенде. Проверяются реальные действия в интерфейсе, сохранение результата после обновления страницы и границы доступа семи стартовых ролей. Этот план дополняет [руководство пользователя](user-handbook.md) и короткий [чек-лист приёмки](manual-acceptance-small-team.md).

**Граница проверки:** продажи, закупка, расчёты, документы, оплаты, согласование, поставка, настройки и повседневная работа команды. Нагрузочные испытания, перенос старой базы и юридическая корректность ставок конкретной компании здесь не оцениваются. Все суммы, контрагенты и документы должны быть учебными.

## 1. Как фиксировать результат

Для каждого ID записывайте **PASS**, **FAIL**, **BLOCKED** или **N/A**. PASS означает, что совпали и видимый результат, и сохранённые данные после повторного открытия записи. FAIL требует номера дефекта. BLOCKED означает, что не выполнено предусловие, с указанием его ID. N/A допустим только с объяснением, почему шаг неприменим к данной конфигурации. Если сервер вернул ошибку в отрицательном сценарии, убедитесь, что новая запись не появилась и суммы не изменились.

**P0** — без прохождения нельзя принимать CRM для работы: вход и права, заявка, квота, расчёт, КП, счёт, деньги и исполнение. **P1** — важная повседневная функция или удобство; отклонение документируется и отдельно принимается владельцем. Для доступов критерием служит серверный отказ **403/404 без содержимого**, даже если интерфейс по ошибке показывает кнопку или прямой адрес страницы.

Если «Сохранить» не даёт результата, откройте в инструментах браузера вкладку **Network → Fetch/XHR**, повторите один раз и запишите, появился ли запрос POST/OPTIONS, его адрес, код и текст ответа. Отсутствие POST тоже является результатом диагностики: проверьте подсказки в самой форме и сообщите о дефекте. Не включайте в отчёт cookie, пароль, секретные ключи и полные заголовки авторизации.

| Поле протокола | Что записать |
|---|---|
| Сборка и среда | Дата, SHA коммита или версия архива, адрес тестового стенда, браузер |
| Исполнитель и роль | Кто тестировал, под какой учётной записью |
| Данные | Номер заявки, КП, счёта, платежа, волны; учебный профиль |
| По каждому кейсу | ID, PASS/FAIL/BLOCKED/N/A, фактический результат, номер дефекта и время |
| Для дефекта | Предусловия, точные шаги, ожидание и факт, роль, номер записи, текст ошибки/скриншот, серьёзность, повторяемость, исправление и повторная проверка |

## 2. Подготовка стенда и данных

1. Распакуйте архив проекта в новую папку и откройте [инструкцию передачи](handover-deployment.md). Создайте отдельный .env командой **python3 scripts/init-env.py**, затем выполните **docker compose build api web** и **docker compose up -d --no-build**. Дождитесь healthy для db, clamav, api и web, завершения migrate с кодом 0 и состояния Up у worker. Адрес интерфейса по умолчанию — **http://127.0.0.1:8080/**.
2. **Только на пустой базе** выполните **python3 scripts/setup_demo_roles.py**. Семь логинов и новых случайных паролей будут в локальном файле .runtime/demo-role-credentials.txt с правами 0600. Не вставляйте их в отчёт, скриншоты или архив. Для проверки смены ролей используйте выход из CRM или второе приватное окно.
3. До изменения прав проверьте стартовую матрицу ниже. Для экспериментов с правами запланируйте **отдельного восьмого сотрудника**, которого создадите в ACC-06; не меняйте семь исходных учёток до завершения ролевых кейсов.
4. Зафиксируйте дату проверки **T** и подготовьте маленький файл **qa-note.txt** без персональных данных. Запланируйте имена: организация продавца **QA Продавец**, клиенты **QA Клиент А** и **QA Клиент Б**, поставщик **QA Поставщик**, проверенный товар с CAS **64-17-5**, потребность **10 кг** и квота в RUB до **T+30 дней**. Сами записи создавайте в CFG-01, CRM-01, CRM-04 и BUY-01/04, чтобы проверить их сохранение, а не подменять кейсы готовыми данными. Для частичного принятия 5 из 10 кг установите в квоте минимум не более 5 кг, кратность 1 кг и совместимую фасовку товара.
5. До CFG-04 запишите на бумаге значения **учебного** финансового профиля: ставки, округление, порог финансирования, разрешение частичного принятия и два расчётных эталона. Сам профиль создаётся и публикуется в CFG-04/05. Нулевые значения в стартовой форме — заготовка, а не утверждённые правила компании.
6. Основную **заявку А** с тестовой отметкой создайте в CRM-04. Чужую менеджеру **заявку Б** руководитель создаёт непосредственно перед ACC-04, после CFG-01 и CRM-01; не предоставляйте её менеджеру. Для проверки отчётов Б может быть синтетической без тестовой отметки. Отдельные заявки/счета используйте для аннулирования, аналога и переноса волны, чтобы отрицательный тест не разрушил основной сценарий. ACC-04 выполняйте после CRM-04, ACC-05 — после ACC-06, хотя они стоят в разделе доступов.

**Порядок основного прохода:** Администратор → Менеджер продаж → Закупщик → Владелец расчётов → Менеджер продаж → Финансовый контролёр → Руководитель → Логист. Передавайте следующему участнику номер заявки А. После каждого изменения проверяйте запись повторным открытием и обновлением страницы.

### Стартовые роли: что должно и не должно работать

| Роль | Основной доступ | Контрольное ограничение |
|---|---|---|
| Администратор | Сотрудники, роли, организация, рабочие правила, аудит | Нет просмотра заявок и финансовых расчётов по умолчанию |
| Руководитель | Заявки команды, назначение, согласования, аналитика, волны | Не подтверждает оплату и не редактирует финансовый профиль |
| Владелец расчётов | Финансовый профиль, квоты, подробные суммы и версии расчёта | Не выпускает КП/счёт без дополнительного права |
| Менеджер продаж | Свои и явно предоставленные заявки, клиенты, звонки, КП, счета, заявление оплаты | Не видит закупочную цену/прибыль и не подтверждает поступление |
| Закупщик | Номенклатура, запросы поставщикам, квоты, закупочная цена | Не записывает финансовый расчёт и не проводит оплату |
| Логист | Волны и события поставки | Не меняет деньги и финансовый профиль; скачивание файла требует отдельного права |
| Финансовый контролёр | Заявление, подтверждение, распределение и обратная операция по оплате | Не выпускает КП и не меняет формулы |

Область «свои/предоставленные» включает собственную запись **и** заявку, доступ к которой явно выдан пользователю. После изменения роли или персональных прав ожидаемая матрица меняется; ролевые кейсы ниже относятся к стартовой конфигурации.

## 4. Решение по результатам

CRM готова к ручной сдаче, когда:

1. Все P0 имеют PASS; среди открытых дефектов нет потери данных, неверного долга/количества, выдачи чужой записи или финансовых полей, ошибочного КП/счёта и нарушения роли.
2. Семь стартовых пользователей вошли, их разрешённые действия выполнены, запреты проверены под правильной ролью, включая прямое открытие чужой заявки/файла.
3. Учебный финансовый профиль проверен независимыми числовыми примерами; КП и счёт открываются, имеют нужный номер, строки и реквизиты. Это **не** утверждает ставки для реальной компании.
4. Для каждого P1 с FAIL есть дефект, обходной путь и явное решение владельца: исправить до запуска или принять как ограничение.
5. Итоговый протокол содержит версию кода, дату, тестовые номера, результаты по ID и повторную проверку исправленных дефектов. Только после этого отдельно утверждаются реальные реквизиты, формулы и доступы для рабочей базы.

**Шаблон одной записи результата:** «PAY-03 | PASS | 24.09, Финансовый контролёр | заявка А №…, счёт №…, платёж №… | долг до/после: …/… | дефект: нет». При FAIL приложите ожидаемое и фактическое числовое значение, а не только скриншот сообщения.
