# Методика нагрузочного и стресс-тестирования (R15, S15, S18)

## 1. Цели и регламент SLA

Нагрузочное тестирование CRM системы предназначено для верификации устойчивости, задержек (latency) и отказоустойчивости при пиковых нагрузках, а также для измерения Recovery Time Objective (RTO) при отказе и перезапуске фонового воркера.

### Пороговые значения SLA:
- **P95 Latency на чтение и поиск:** $\le 2.0$ сек (целевое $< 0.1$ сек).
- **P95 Latency расчёта из 100 строк:** $\le 1.0$ сек (целевое $< 0.05$ сек).
- **P95 Latency генерации PDF/XLSX (100 строк):** $\le 2.0$ сек (целевое $< 0.1$ сек).
- **Парсинг и валидация реестра импорта (10 000 строк):** $\le 3.0$ сек ($> 30\,000$ строк/сек).
- **Допустимый процент ошибок (Error Rate):** $\le 1.0\%$ (в штатном режиме $0\%$).
- **Recovery Time Objective (RTO) воркера:** $\le 10.0$ сек (целевое $< 1.0$ сек).

## 2. Реалистичные сценарии нагрузки

В отличие от устаревших тестов с синтетическими cookies (`scripts/load_test.py`), обновленная версия выполняет полный жизненный цикл:

1. **Реальная аутентификация пользователя (Auth & Session):**
   - Выполняется `POST /api/v1/auth/login` с передачей реальных учетных данных.
   - Фиксируется сессионная cookie `crm_session` и `X-CSRF-Token`.
   - Проверяется защита от перебора паролей (Advisory locks и лимиты попыток).

2. **Поиск по каталогу, заявкам и контрагентам (Search & Query Concurrency):**
   - `GET /api/v1/requests?page=1&page_size=20` — первая страница заявок;
   - `GET /api/v1/requests?page_size=20&stage=new` — фильтрация по стадии сделки;
   - `GET /api/v1/requests?page_size=50&q=test` — поиск по заявкам;
   - `GET /api/v1/analytics/dashboard?date_from=...&date_to=...` — сводный аналитический отчет;
   - `GET /api/v1/counterparties?page_size=20` и `?q=клиент 12` — реестр контрагентов и поиск по нему;
   - `GET /api/v1/nomenclatures?page_size=100`, `/api/v1/tasks?page_size=50`, `/api/v1/payment-calendar?page_size=100` — каталог, задачи и платёжный календарь.

3. **Сложный расчёт из 100 товарных позиций (Calculation Engine 100 lines):**
   - Граничный стресс-тест интерпретатора формул `app.commerce.calculator.calculate()`.
   - Включает 100 спецификаций, импортные пошлины, НДС, конвертацию валют, пропорциональное распределение накладных расходов и проверку инвариантов сумм без погрешностей `float`.

4. **Генерация официальных документов и PDF (PDF Export):**
   - Формирование коммерческого предложения на 100 строк.
   - Сборка бинарного PDF файла движком ReportLab с поддержкой кириллицы (Unicode) и параллельное создание XLSX.
   - Запись в файловое хранилище с вычислением SHA-256 хеша.

5. **Пакетный импорт 10 000 строк (Batch Import):**
   - Генерация в памяти XLSX-файла на 10 000 контрагентов.
   - Потоковый разбор строк (`parse_rows`), валидация ИНН, телефонов, адресов и поиск совпадений.

6. **Отказоустойчивость воркера и RTO (Worker Resilience & Recovery):**
   - Помещение задачи в транзакционную очередь `outbox_events`.
   - Имитация аварийного завершения воркера (SIGTERM / crash) в момент обработки.
   - Проверка автоматического отката транзакции PostgreSQL: статус задачи сохраняется (`pending`), данные не повреждаются.
   - Запуск воркера после рестарта, успешное завершение задачи (`succeeded`) и фиксация времени восстановления RTO.

## 3. Запуск нагрузочных тестов

### Подготовка данных

Замеры на пустой базе ничего не говорят о списках и поиске. `scripts/seed_large_db.py` наполняет отдельную базу синтетической CRM: при `--scale 1.0` это 100 000 клиентов, 50 000 заявок по три позиции с квотами, 20 000 задач и 20 000 плановых платежей. Создайте для этого новую базу, примените миграции и заполните её:

```bash
DATABASE_URL=postgresql+psycopg://…/crm_load alembic -c backend/alembic.ini upgrade head
DATABASE_URL=postgresql+psycopg://…/crm_load python3 scripts/seed_large_db.py --scale 0.2
```

Скрипт не удаляет данные и отказывается работать при `ENVIRONMENT=production`. Записанную историю база удалять не даёт, поэтому для повторного замера создайте базу заново.

### Запуск

Скрипт `scripts/load_test.py` может выполняться как против живого HTTP-сервера, так и напрямую через ASGI транспорт приложения FastAPI.

### Команды запуска:

```bash
# Базовый нагрузочный тест (10 параллельных пользователей, 1000 строк импорта)
python3 scripts/load_test.py --concurrency 10 --requests 3 --import-rows 1000

# Полный стресс-тест (10 пользователей, 10 000 строк импорта, выгрузка JSON отчета)
python3 scripts/load_test.py --concurrency 10 --requests 3 --import-rows 10000 --report reports/load_test_report.json

# Запуск против внешнего адреса стенда
python3 scripts/load_test.py --url http://api.crm.internal:8000 --email loadtest@crm.example.com
```

### Параметры CLI:
- `--url`: адрес API (по умолчанию `http://localhost:8000`);
- `--email` / `--password`: учетные данные тестировщика. Скрипт создаёт эту учётную запись со всеми ролями в базе из `DATABASE_URL`; без `--password` ей задаётся новый случайный пароль при каждом запуске;
- `--concurrency`: число одновременных сессий пользователей;
- `--requests`: число циклов запросов на каждого пользователя;
- `--import-rows`: объем строк для теста импорта (по умолчанию `10000`);
- `--max-p95`: лимит P95 задержки в секундах (по умолчанию `2.0`);
- `--max-error-rate`: лимит процента ошибок (по умолчанию `1.0%`);
- `--report`: путь к файлу JSON для сохранения метрик;
- `--allow-production`: разрешить запуск при `ENVIRONMENT=production` (без флага скрипт отказывается).

При превышении любого порога SLA скрипт завершается с кодом **1**, что гарантирует блокировку неуспешных релизов в CI/CD.

## 5. Грациозная остановка и сценарии деградации (Graceful Stop)

В воркере `app/communication/worker.py` реализован перехват системных сигналов `SIGTERM` и `SIGINT`.
- При поступлении сигнала воркер завершает текущий батч событий и фиксирует изменения в БД;
- Ожидание между итерациями реализовано через кванты по 100 мс, что позволяет мгновенно реагировать на завершение контейнера без зависания;
- В случае принудительного `kill -9` транзакционный механизм PostgreSQL `with_for_update(skip_locked=True)` гарантирует автоматическое освобождение блокировок строк и возврат событий в статус `pending` без дублирования бизнес-эффектов.
