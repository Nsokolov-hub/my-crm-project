# Контроль работы ИИ-разработчика

Этот документ задаёт доказательства для независимой проверки. Он не запускает автоматическое наблюдение за GitHub. Когда владелец подключит куратора, нужно передать доступ к репозиторию, ветку/PR и отчёт по конкретному commit SHA.

## 1. Какой результат считать итерацией

Одна итерация закрывает один этап или законченный подэтап S00–S20. Большой этап делится на несколько PR с независимыми результатами. Исследование без кода допустимо для baseline и архитектурного решения, но не заменяет реализацию последующих задач.

Пример хорошей единицы работы: «Запретили возврат закрытого snapshot при повторе расчёта после отзыва права; воспроизвели старую утечку, исправили проекцию ответа, сохранили идемпотентность и добавили PostgreSQL-регрессию».

Пример недостаточного результата: «Улучшили безопасность, все страницы работают». В нём нет проверяемого поведения, версии кода и свидетельства.

Не увеличивать оценку готовности по числу написанных строк, файлов, экранов, коммитов или тестов. Прогресс — закрытое требование с доказательством, а не переименование PARTIAL в DONE.

## 2. Шаблон отчёта разработчика

Сохранять отчёт в `docs/reports/Sxx-short-topic.md`; машинные результаты CI/тестов можно хранить как артефакты с ссылками. Не складывать секреты или реальные клиентские данные в отчёт.

```text
Этап и задача:
Требования F/N/A:
Репозиторий и ветка:
Base SHA:
Head SHA:
PR или локальный commit/patch:

Исходный сценарий и ошибка:
Ожидаемое поведение:
Реализованное поведение:
Основные изменённые файлы:

Как проверить вручную:
1. Исходные тестовые данные и роли.
2. Действия в интерфейсе или API.
3. Ожидаемые записи, суммы, права и статусы.

Проверки:
- Команда / окружение / exit code / passed-failed-skipped / ссылка на вывод.
- Какие проверки НЕ запускались и почему.
- Какой дефект воспроизводился до исправления.

Данные и совместимость:
- Новые миграции, версии до/после.
- Сохранность старых документов и snapshots.
- Изменение API и обновление UI.
- Блокировки/повторяемость/права/аудит.
- Откат и восстановление.

Известные ограничения и открытые дефекты:
Что обновлено в traceability/acceptance:
Следующая задача и её зависимости:
```

Если HEAD изменился после тестов, отчёт больше не доказывает состояние нового HEAD. Повторить затронутые проверки и указать новую версию. Скриншот CI без SHA и контекста не является достаточным свидетельством.

## 3. Проверка куратором

1. Сопоставить просьбу пользователя, конкретное требование ТЗ и границы PR. Проверить, что не добавлена незаказанная бизнес-логика.
2. Изучить diff, связанные сервисы, схемы, миграции и текущие тесты. Не доверять только итоговому описанию автора.
3. Воспроизвести найденный дефект/новую функцию на отдельной среде. Для денег и конкурентности использовать PostgreSQL; SQLite не подтверждает блокировки и триггеры.
4. Проверить положительный и отрицательный сценарии с обычными ролями. Администратор с семью ролями не доказывает правильность разграничения.
5. Проверить соседние последствия: старые документы, пропущенные права через экспорт/чат, повтор после потери ответа, concurrency, история и баланс.
6. Прогнать проверки, соответствующие риску PR, и оценить, покрывают ли тесты требование, а не повторяют внутренние функции.
7. Проверить UI на реальном API, если изменён пользовательский путь. Показать результаты и оставшиеся ограничения без заявления о непроведённых проверках.
8. Вынести решение: ACCEPTED, CHANGES_REQUIRED или NEEDS_EVIDENCE. Решение по конкретному этапу не равнозначно готовности всей CRM.

Куратор может исправить небольшой локальный дефект отдельным коммитом и повторить проверки. Если проблема меняет модель данных или бизнес-правило, вернуть разработчику узкую задачу с воспроизводимым примером и ожидаемым результатом, сохранив общую архитектуру.

## 4. Глубина проверки по риску

| Изменение | Минимально необходимое подтверждение |
|---|---|
| Деньги, налоги, частичные количества | Ручные контрольные числа, Decimal/rounding-инварианты, отрицательные случаи, повтор, история, PostgreSQL при конкуренции |
| Разрешения и проекции | own/shared/all/deny, связанные объекты, роль отозвана в активном сеансе, прежний idempotency key, API/экспорт/чат/файл |
| Миграция | Пустая база, обновление с данными, сохранность snapshots/files, DDL-права, запрет/разрешение триггеров, документированный откат |
| Очередь и интеграционный сбой | Повтор, две обработки, откат частичных изменений, terminal failure, реальный restart, отсутствие потерянного эффекта |
| UI-форма | Реальный API, валидация, отсутствие потери черновика, 409/403/сеть, сохранение и повторное открытие |
| Аналитика | Ручная контрольная выборка, даты и timezone, текущий/исторический владелец, альтернативы/отмены, разные валюты, drilldown и XLSX |
| Backup/restore | Восстановленная отдельная среда, связи/балансы/hashes, проверка повреждения, измеренные RPO/RTO |
| Косметика/тексты | Сборка и визуальная проверка затронутого состояния; не нужны искусственные тесты, копирующие CSS |

## 5. Условия немедленного возврата на исправление

- Код способен раскрыть закрытые финансовые поля, личный чат или файл.
- Происходит финансовый дубль, превышение суммы/количества, отрицательный остаток или необъяснимое расхождение итогов.
- Сохраняемый документ/расчёт незаметно меняется от обновления справочника или шаблона.
- История подтверждённых операций удаляется/редактируется вместо отдельного исправления.
- Новый состав использует старое согласование; фактически отправленный товар исчезает из-за отмены оплаты.
- Тесты, проверки прав или ограничения ослаблены ради зелёного CI без согласованного изменения требований.
- Проверка помечена PASS, хотя пропущена, использует mock вместо проверяемого сервиса или выполнена на другом SHA.
- Миграция/restore может повредить рабочую среду по умолчанию; секреты включены в Git/логи/артефакты.
- Обязательная функция показана кнопкой, которая не выполняет обещанный результат.

## 6. Статусы требований и контроль готовности

Использовать отдельные признаки реализации и проверки:

- NOT_IMPLEMENTED — реализации нет.
- PARTIAL — часть поведения или экранов отсутствует.
- IMPLEMENTED_UNVERIFIED — код есть, требуемого доказательства нет.
- VERIFIED — конкретное требование прошло перечисленные проверки на данном SHA.
- EXTERNAL_DEPENDENCY — только конкретная часть зависит от реальных данных, инфраструктуры или решения владельца.
- P2 / P3 / OUT_OF_SCOPE — сознательно другая очередь/граница.

Общий статус этапа ACCEPTED назначается после проверки куратора, когда он подключён. До независимой проверки разработчик пишет READY_FOR_REVIEW и продолжает разрешённые независимые работы. Не блокировать весь проект ожиданием формального одобрения каждого мелкого коммита.

Процент готовности переоценивать после группы завершённых этапов, сохраняя те же категории из READINESS. Не прибавлять одинаковые 5% за любой этап: исправление критичного доступа и новый цвет кнопки имеют разный вес.

## 7. Что передать мне для дальнейшего контроля

Когда потребуется подключить куратора, достаточно сообщения следующего вида:

```text
Проверь работу другой ИИ по CRM.
Репозиторий: <ссылка>
Ветка/PR: <ссылка или имя>
Проверяемый commit SHA: <значение>
Этапы: Sxx, задачи ...
Отчёты: docs/reports/...
CI: <ссылка>
Известные проблемы: ...
Нужно: проверить код и фактическое выполнение плана, воспроизвести критичные
сценарии, исправить локальные дефекты или сформировать точные задачи возврата.
```

Для закрытого репозитория потребуется доступ в подключённой среде. Текстовый отчёт без кода позволяет проверить лишь полноту описания, а не качество реализации. Производственные пароли и реальные клиентские данные передавать в сообщении не нужно.
